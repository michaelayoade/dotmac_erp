# Generated documents on the dotmac-files tenant plane — design

**Status:** Design, decided 2026-10-26 (Michael). Implementation deferred
until the Phase 0 deploy of `bcc32dbc` is proven in production.
**Scope decision:** all four generated families move. One storage owner for
every generated byte; no permanent second path.
**Companion decisions:** ADR-0014 (`docs/adr/0014-generated-documents-have-one-storage-owner.md`);
numbering/files user-upload cutovers #722–#747 are the precedent.

## What exists today (measured at `2a60a54c`)

Four families produce bytes server-side. None of them uses the
`dotmac-files` seam that every user-upload family now uses
(`prepare_upload` + `stage_tenant_file_if_unreserved` in
`app/services/file_object_cleanup.py`, provider
`app/services/storage.py::DotmacFilesS3Provider`).

| Family | Producer | Persisted today? | Record of the bytes |
|---|---|---|---|
| Payslip PDFs | `app/services/people/payroll/payslip_pdf.py` (WeasyPrint) | **No** — regenerated on every view/email | none |
| Template-generated documents | `app/services/automation/document_generator.py` | Yes, legacy `FileUploadService` (`generated_docs` prefix) | `GeneratedDocument.file_path`, `content_hash`, `superseded_by`, `document_number` |
| Report instances | `app/services/finance/rpt/report_instance.py` | Yes, legacy (`generated_reports` prefix) | `ReportInstance.output_file_path`, `generated_by_user_id`, schedule `retention_days` |
| Async exports | `app/services/finance/rpt/async_exports.py` + `app/tasks/finance.py` | Yes, same report plumbing | `ReportInstance` rows; requester emailed a download link |

Downloads today: `/files/generated/{document_id}` and legacy
`/uploads/generated_docs/{org_id}/{filename}` (`app/api/files.py`), plus
per-report download bases. Retention today: `cleanup_old_instances`
deletes report rows after `retention_days` but leaves the objects to the
orphan-reconciliation machinery (debt item E5).

Out of scope, deliberately: synchronous generate-and-stream responses with
no persistence (inline exports at or below
`INLINE_EXPORT_ROW_THRESHOLD`, invoice PDF rendering — invoices move with
`dotmac-billing`, ADR 0020/Sub track), and email bodies.

## The one behavioural change: payslips become stored artifacts

Payslips are the only family with no stored bytes. Regeneration means a
template, branding or formatter change silently rewrites the payslip an
employee was originally issued — the rendered PDF is a financial record,
not a view. This design therefore does **not** lift payslips onto the
files plane as-is; it changes what a payslip PDF *is*:

- The PDF is generated **once, at salary-slip posting**, staged on the
  tenant plane in the posting transaction's follow-up (the existing
  `send_payslip_email` task becomes the staging point: it already renders
  exactly the bytes that get emailed — those bytes become the artifact).
- Self-service (`/people/self/payslips/...`) and HR downloads serve the
  stored artifact, never a re-render.
- A re-issue renders a **new** artifact and supersedes the old one
  (provider `put` is immutable/checksum-bound; nothing overwrites).
- Pre-cutover slips have no artifact: first download renders, stages, and
  serves (render-on-miss backfill), so no bulk backfill window is needed.

If this is wrong — if payslips must always reflect current branding — the
family drops out of this design unchanged; everything below is unaffected.

## Target design (all four families)

### Writing

Every family writes through the existing user-upload seam, unchanged:

1. Producer renders bytes in memory (as today).
2. `prepare_upload(provider, scope=tenant_scope(org_ctx), policy=<family
   policy>, original_filename=<display name>, declared_media_type=<family
   constant>, chunks=...)`. Generated bytes are known-good, but they go
   through the same signature/size policy as uploads — no privileged lane.
   Family policies: payslips/reports/documents = PDF (+ HTML for template
   documents where `OutputFormat` allows); exports = CSV/PDF per
   `EXPORT_DEFINITIONS.formats`. Size ceilings are per family settings,
   sized for the export case explicitly.
3. `stage_tenant_file_if_unreserved(db, prepared=...)` inside the
   producer's transaction, and the owning row records the staged file id
   instead of a storage path:
   - `GeneratedDocument.file_id` (new column; `file_path` frozen for
     pre-cutover rows),
   - `ReportInstance.output_file_id` (ditto),
   - `SalarySlip.payslip_file_id` (new; null = pre-cutover, render-on-miss).
4. Generation failure after staging stays a domain failure exactly as
   today; the transaction rule is the user-upload one — no staged row
   without its owning row, no owning row pointing at an unstaged file.

Worker contexts (Celery: payslip email, scheduled reports, async exports)
already run under `session_for_org` / `for_each_organization`, which is
what the seam requires; `generated_by_user_id` stays the audit actor for
user-initiated runs, and scheduled/system runs keep theirs. Nothing
cross-org is introduced.

### Reading

- One staged download path per family, replacing the `get_storage()`
  branches in `app/api/files.py` and the report download handlers: load
  owning row under the caller's org scope -> staged file -> streamed
  response (the cut families' handlers are the template).
- Legacy branches keep serving pre-cutover rows (`file_path` set,
  `file_id` null) until the backfill below completes — the same staged/
  legacy split every upload family used.
- Async export email links keep pointing at the existing authenticated
  download routes; only the handler's storage source changes.

### Retention and deletion

- Report instances/exports: `cleanup_old_instances` gains the duty it
  currently skips — deleting the staged file (record + object) in the
  same pass that deletes the instance row. Orphan reconciliation remains
  the safety net, no longer the mechanism. Its reference view must learn
  the three new `file_id` columns in the same slice that introduces each
  (two-directional ratchet, as with the upload families).
- Generated documents: supersede never deletes; explicit document
  deletion deletes the staged file with the row (current legacy delete
  behaviour, moved to the seam).
- Payslips: no retention deletion. Payslip artifacts live and die with
  the salary slip under existing payroll retention rules.

### Backfill

Template documents and report instances with live `file_path` values get
the standard per-family backfill script (dry-run first, one transaction
per record, idempotent, legacy objects left for orphan reconciliation) —
two more scripts in the exact shape of the thirteen upload ones. They run
**after** the upload-family backfills, in the same operational pattern.
Expired report outputs are not backfilled; retention wins.

## Slice plan (each: family PR -> backfill window -> legacy branch delete)

1. **Payslips** — smallest blast radius, proves persist-at-posting.
2. **Template-generated documents** — durable, lowest volume.
3. **Report instances + async exports together** — one plumbing change;
   includes the retention-delete duty and the reference-view update.
4. **Retirement** — delete `get_generated_docs_upload`,
   `get_generated_report_upload` and the legacy generated download
   branches once backfills verify zero legacy reads; `app/api/files.py`
   legacy `/uploads/generated_docs/...` route goes with them.

Ordering constraints: Phase 0 deploy proven first; the 13 upload backfills
may run before, between, or after these slices (independent families),
but legacy storage retirement (Phase 1 close-out) waits for both sets.

## Non-goals

- No new Starter module work is expected: `dotmac-files` 0.1.0a7 already
  detects PDF/CSV/text; if HTML template output needs a detection ruling
  it is a policy constant change in ERP, not a module change (generated
  HTML is first-party bytes, unlike user SVG).
- No change to rendering (WeasyPrint/templates), numbering of generated
  documents, report scheduling, or export thresholds.
- No public/presigned URLs: authenticated streaming stays the rule.
