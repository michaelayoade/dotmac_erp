# Departmental KPI Dashboard — implementation assessment

## Existing system

The People/Performance module already owned employee KPI records in
`perf.kpi`, KRA relationships, appraisal scorecards, KPI CRUD pages and APIs,
department and employee master data, position-based hierarchy, support-ticket
metric calculation, reports, and performance-mode policy guards.

`perf.department_performance_template` already represented a useful first
version of a department KPI configuration. It held the department, target,
weight, metric source, direction flag, and active state, and could expand a
template into employee KPI records for a period. Existing `perf.kpi` rows
already preserve employee-specific target, actual, period, weight, status, and
evidence.

## Gaps found

- Department templates were generated by matching department names to a large
  Python dictionary. Adding or renaming a department could silently select the
  wrong KPI set.
- The KPI model assumed higher-is-better in its primary progress update path
  and used a fixed 80 percent status boundary.
- There was no management screen for department KPI configuration.
- Department, staff, and KPI drill-down dashboards were absent.
- Configurations lacked stable codes, measurement types, frequencies,
  configurable thresholds, target-band scoring, and role/position/employee
  assignment scope.
- Manual updates overwrote the current KPI without an immutable measurement
  revision or configuration snapshot.
- Automatic metrics were discovered partly by searching KPI names and notes
  instead of following an explicit configured data-source key.
- Existing KPI routes relied on broad HR access; dedicated KPI permissions did
  not exist.

## Implemented architecture

The existing models are extended rather than replaced:

1. `DepartmentPerformanceTemplate` is the database-managed KPI definition and
   department assignment. A configuration can optionally narrow applicability
   to an existing designation, position, or employee.
2. `KPI` remains the immutable-period employee assignment/result and now links
   to its configuration with a scoring snapshot.
3. `KPIMeasurementHistory` records every manual or automatic measurement,
   score, approval state, actor, evidence, and configuration snapshot. A new
   manual revision supersedes an older pending revision; approved values alone
   are published to the KPI result.
4. `KPIConfigurationAudit` appends before/after configuration revisions.
5. `DepartmentalKPIService` is the single scoring and aggregation boundary for
   higher-is-better, lower-is-better, and target-band KPIs.
6. Department and employee dashboards read HR departments and employees
   dynamically. No department identifier or KPI definition exists in code.
7. Management dashboards use the shared Chart.js wrapper for department and
   KPI history and expose a permission-controlled CSV export of the filtered
   view.

The old department-name generator remains as a compatibility callable but no
longer creates anything. It reports the number of administrator-managed
configurations so old callers fail safely without reintroducing hardcoded
business rules.

## Data sources

The first explicit adapters use existing `support.ticket` data for resolved
ticket count, open backlog, resolution rate, and average resolution days.
Unknown source keys report an unavailable-source error and never fabricate a
value. A blank source key selects the audited manual workflow.

## Historical behavior

Configuration changes increment `config_version`; previously instantiated KPI
rows retain their target, weight, and JSON scoring snapshot. New measurements
create audit revisions instead of deleting the previous value. Dashboard
calculations for historical periods use the saved target, weight, direction,
and thresholds rather than the current configuration. Existing legacy
KPI rows remain available through the original pages and are linked to a
department configuration during migration when department and KPI name match.

## Known limitations

- The generic ERP hierarchy has departments, designations, positions, and
  employees but no cross-module generic team entity. This implementation uses
  those canonical relationships and does not duplicate Support teams.
- Only Support ticket automatic adapters are enabled initially. Other modules
  can register explicit source keys as their metric definitions are approved.
- The central calculation service caps scores at 100. Alternative caps or
  stepped scoring curves require another registered calculation strategy.
- Configuration weights may be saved below 100 percent while a manager is
  building a scorecard, but the combined active assignments applicable to an
  employee may never exceed 100 percent. The management and dashboard pages
  show average/minimum/maximum assigned weight and mark whether every active
  employee totals exactly 100 percent.
